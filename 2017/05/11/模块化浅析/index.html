模块化浅析

Posted on 2017-05-11

子曰：简单性和模块化是软件工程的基石；分布式和容错性是互联网的生命。

这篇的标题挂了很久，正文一直空着，补一段自己的理解。

模块化说白了就是把一个 App 拆成几块：基础库放网络、图片、工具类这些谁都要用的东西；业务模块按功能切，比如登录、订单、消息；最外面留一个 app 壳，负责组装和打包。每块单独一个 module，依赖关系单向，业务模块之间尽量不互相引用。

好处很直接。改一个业务模块，只编译它和 app 壳，不用每次全量编译，等的时间少很多；几个人可以同时改不同的模块，冲突也少；哪天要把这块逻辑搬到别的 App，整个 module 拿过去就行。

麻烦的地方在通信。模块之间不能直接 new 对方的 Activity 或者调对方的类，一般靠路由跳页面，靠下沉的接口拿服务，实在不行用事件总线。接口下沉这层要提前想清楚，不然拆完发现到处互相依赖，还不如不拆。

还有资源问题。多个 module 里的 strings、color、布局名字容易撞，命名最好带上模块前缀；AndroidManifest 合并也时不时出岔子，出问题先看合并后的清单。

我的看法是，模块化不是拆得越细越好。业务还没稳定的时候硬拆，后面改需求要同时动好几个 module，反而更累。先按基础库 / 业务 / 壳分三层，等某个业务真的长大了再单独拆出去，比较稳。
