AIDL的梳理

Posted on 2017-02-20

Android 的 IPC 方式有广播、Bundle、ContentProvider、Socket，还有 AIDL。其中 AIDL 是最关键的一种。

AIDL 背后绕不开 Binder。在我看来，Binder 就是连接客户端和服务端的一座桥。

下面按《Android 开发艺术探索》的思路，先生成 IBookManager.java，看看 AIDL 到底帮我们写了什么。

Stub、Proxy 和 onTransact

Stub 就是服务端的 Binder 类，DESCRIPTOR 是这个 Binder 的唯一标识，这里直接用了接口的全类名。

asInterface(IBinder obj) 负责把服务端的 Binder 转成客户端要用的接口：同进程直接返回 Stub，跨进程则包一层 Proxy。

asBinder() 返回底层的 Binder 对象。

onTransact(int code, Parcel data, Parcel reply, int flags) 运行在服务端的 Binder 线程池里。客户端发起 IPC 请求后，最终由它处理：根据 code 判断调用哪个方法，从 data 里取出参数，再把结果写进 reply。返回 false 表示这次请求失败。

Proxy 里的 getBookList() 则相反：先准备好 data 和 reply，有参数就写进 data，然后调用 transact() 发起请求并挂起当前线程，等 onTransact 写完 reply 再取结果。

几个注意点

  • 客户端发起请求后线程会挂起。为了不影响 UI 线程，耗时调用要放到子线程，服务端同理。
  • onTransact 运行在 Binder 线程池中，实现必须是线程安全的。
  • 两端任何一个方法耗时，调用方都要在子线程里调用。
  • 解绑接口时用 RemoteCallbackList，由它统一维护跨进程的回调接口。
  • 服务进程意外断开时，可以在 serviceDisconnected 里重连，也可以给 Binder 设置死亡代理 DeathRecipient。我个人觉得前者更好用。
  • AIDL 的权限校验可以放在 onBind 或 onTransact 里，另外还可以做包名校验。

以上就是对 Binder 的分析。AIDL 本质上就是对 Binder 的一层封装。
