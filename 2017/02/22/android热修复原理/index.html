android热修复原理

Posted on 2017-02-22

当时常用的热修复技术，大概分三类：

  • AndFix：Native hook 方案。
  • Nuwa、HotFix、RocooFix：QQ 空间提出的 ClassLoader 替换类方案。
  • Tinker：Instant Run 冷插拔原理的 Dex 替换。

Native hook

在 native 层做指针替换。AndFix 基于修复包和原生包的差异生成注解，通过这份注解找到要替换的方法，条件满足就 hook 掉并替换。

Dex 分包

Nuwa、HotFix、RocooFix 这些方案都是基于 dex 分包。

什么是 dex 分包？先看 DexOpt。Android 系统安装一个应用时，有一步是对 Dex 做优化，专门干这事的工具叫 DexOpt。它在第一次加载 Dex 文件时执行，会生成一个 ODEX 文件，也就是 Optimised Dex。ODEX 的执行效率比直接执行 Dex 高很多。

但早期的 Android 系统里，DexOpt 有两个问题：

  1. DexOpt 会把每个类的方法 id 检索出来，存进一个链表，而链表的长度是用 short 保存的，所以方法 id 不能超过 65536 个，也就是一个 dex 文件最多支持 65536 个方法。（官方后来提出了 multidex 方案。）
  2. DexOpt 用 LinearAlloc 存储应用的方法信息，而 Dalvik LinearAlloc 是一个固定大小的缓冲区。历史上分别经历过 4M / 5M / 8M / 16M 的限制：Android 2.2 和 2.3 只有 5MB，Android 4.x 提高到 8MB 或 16MB。方法数量太多超出缓冲区，dexopt 也会崩。

因为这两个问题，才有了 dex 分包的方案。

简单说，原理是把编译好的 class 文件拆开打成两个 dex，绕过 dex 方法数量限制和安装时的检查，运行时再动态加载第二个 dex。

原则上两个 dex 里的类是不重复的。那如果 classes.dex 和 classes2.dex 里有重复的类，用到这个类时系统会加载哪一个？

理论知识来了：一个 ClassLoader 可以包含多个 dex 文件，每个 dex 是一个 Element，多个 dex 排成一个有序数组 dexElements。找类时按顺序遍历 dex，在当前 dex 里找到就返回，找不到就继续下一个。

所以有重复的类时，以排在前面的 dex 为准。把有问题的类打进一个 dex（patch.dex），再把这个 dex 插到 dexElements 的最前面，热修复就实现了。

理论到此为止。

Tinker

Tinker 用的是 Instant Run 的冷插拔：完全使用新的 Dex，但又不能直接替换 dex，那怎么办？

编译时用新旧两个 Dex 生成差异包 patch.dex；运行时把 patch.dex 和安装包里的旧 Dex 重新合并，还原成新的 Dex。这里就涉及到怎么把 patch 包算到最优的问题。

这套方案有两个缺点：一是占用更多空间；二是多了一次合成过程。虽然合成放在单独的进程里处理，但合成时间的长短和内存消耗也会影响最终的成功率（跟修改的 Dex 大小、补丁大小有关）。

不过我觉得这两个缺点都不是问题，毕竟热修复本来就不能当更新来用。
