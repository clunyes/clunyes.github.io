android面试分享

Posted on 2017-02-08

这段时间在看机会，跑了几场面试。把印象比较深的题目记下来，既是复盘，也给别人做个参考。先谢谢给我机会的这些公司。

某 AI 公司

面试官非常有耐心，人很好（好想跟他混……）。

  1. OAuth 2.0 的授权流程
    第三方应用先去服务商申请 app secret，然后：

    1. 用户打开客户端，客户端请求用户授权，跳转到服务商页面。
    2. 用户同意并登录，服务商根据用户信息和 app secret 发放 access token。
    3. 客户端拿着 access token 去资源服务器申请资源。
    4. 资源服务器校验令牌，返回对应的数据。

  2. JNI 调用。 具体见 JNI 那篇笔记。

  3. IPC 与 AIDL 的简单实现
    IPC 的方式有广播、AIDL、Messenger、Bundle、ContentProvider、Socket。要理解 AIDL，先得理解 Binder。Binder 就是连接前台应用和 Service 的桥梁。具体实现见《AIDL 的梳理》。

  4. TCP 长连接
    用心跳包来 keep-alive。一个连接在 2 小时内没有任何动作，服务器就向客户机发送探测报文，之后分几种情况：

    • 客户机正常运行且可达，TCP 响应正常，保活定时器复位，再等 2 小时。
    • 客户机崩溃、关机或正在重启，TCP 无响应，75 秒后超时。服务器随后再发 9 个探测报文（共 10 个），间隔都是 75 秒，仍然没有响应就认为连接已关闭。
    • 客户机崩溃后重启完成，服务器会收到一个复位响应，于是终止这个连接。
    • 客户机正常但服务器不可达，10 次探测都没有响应，关闭连接。

  5. Git 命令，git rebase
    公司一直用 SVN，Git 都是我自己在玩，所以这个问题答得一脸懵逼，还是得多补。

  6. SurfaceView 的特性
    SurfaceView 和 View 最本质的区别是：SurfaceView 在新起的单独线程里绘制画面（双缓冲），而 View 必须在 UI 主线程更新。
    它适合内存开销大、刷新频繁的场景，比如游戏、动画、视频。两个关键方法是 lockCanvas() 和 unlockCanvasAndPost()。
    所谓双缓冲，就是 SurfaceView 内部有两块 Buffer：lockCanvas() 之后在 buffer A 上绘图，画完调用 unlockCanvasAndPost() 把 buffer A 显示到屏幕上；再 lockCanvas() 在 buffer B 上绘图，画完显示 buffer B，如此往复。

  7. HTTPDNS
    HTTPDNS 和传统 DNS 的区别在于它走 HTTP 协议，用 HTTP 请求做域名解析，替代原来基于 UDP 的 DNS。
    好处是防劫持、调度更精准，在 App 里用得比较多。落地可以用阿里云的 HTTPDNS，不过是按流量收费的。

  8. ART 和 Dalvik 的区别
    ART 在 APK 安装时就完成编译（AOT），占用空间更多；Dalvik 是运行时动态编译，每次启动都要编译。
    GC 方面，Dalvik 是同步的，ART 做了部分异步化。

  9. 事件分发
    三个关键方法：

    • dispatchTouchEvent()：负责分发事件。
    • onInterceptTouchEvent()：是否拦截当前事件。
    • onTouchEvent()：是否消耗当前事件。
      它们的关系大致是这样： 几个要点：一个事件序列只能被一个 View 消耗；如果没有任何 View 处理，事件会交给 Activity；ViewGroup 的 onInterceptTouchEvent 默认不拦截；View 没有 onInterceptTouchEvent。传递顺序是 Activity → Window → View。

  10. Layout 绘制流程
    Activity 的 attach() 创建 Window 并建立关联，然后 setContentView()：

    1. 如果没有 DecorView 就先创建一个。DecorView 包含标题栏和内容栏（经大神验证，标题栏不是状态栏）。
    2. 把布局 XML 添加到 DecorView 的内容栏 contentParent（R.id.content）。
    3. Activity 回调 onContentChanged()。
    4. 最后在 onResume() 里调用 makeVisible()。
      结构就是 DecorView → ViewGroup（DecorView 的内容栏）→ 你的 View。
      说到这里，必须提一下 Activity、Window 和 View 的关系：View 是视图，但不能单独存在，必须依附在 Window 上，Window 负责展示 View；Activity 负责控制 Window 的行为，Window 的结果再回调给 Activity。两者通过 ViewRootImpl 绑定，它就是 Window 和 View 交互的桥梁。

  11. JVM。 详见这篇。

  12. 内存泄漏
    推荐这篇文章。归总就是一句话：Activity 或 Fragment 里不要持有比自身生命周期更长的引用，否则它就回收不掉。
    常见的几类：Service 没关、内部类持有引用（网络请求）、匿名类持有引用（也是网络请求）。网络请求在退出时务必取消或回收，异步线程引用控件时用弱引用。
    用 MAT 看，depth 为 0 的就是泄漏对象。
    文章最后也给了建议：多线程场景下，RxJava 是很好的解决方案。

某宝公司（电话面试）

  1. Activity 生命周期

    • onCreate：创建。
    • onRestart：从不可见状态切回可见。
    • onStart：已经可见，但还不能交互。
    • onResume：可见且可交互。
    • onPause：仍然可见，但不能交互。
    • onStop：不可见。
    • onDestroy：销毁。
      onPause 和 onStop 通常会一起触发。

  2. Activity 的四种启动模式
    先理解两个概念：

    • task：一组相互关联的 Activity 集合，可以理解为 Activity 在里面活动。
    • taskAffinity：标识一个 Activity 所需任务栈的名字。默认所有 Activity 的任务栈名都是应用包名，主要和 singleTask、allowTaskReparenting 搭配使用。
      然后才是四种模式：
    • standard：默认模式，每次都新建实例。
    • singleTop：栈顶复用。如果栈顶就是这个 Activity，回调 onNewIntent。
    • singleTask：栈内复用。第一次启动时（配合 taskAffinity）新建任务栈，再次启动会把它上面的 Activity 全部弹出，并回调 onNewIntent。还有个特殊参数 allowTaskReparenting，为 true 时会转移任务栈。
    • singleInstance：单独占用一个栈，其余与 singleTask 一致。

  3. 远程 Service 的调用。 就是 localService 和 remoteService 的区别，本质还是上文说的 IPC。

  4. Activity 和 Fragment 的区别，Fragment 的优势
    Fragment 更灵活、更轻量，也更好管理，适配手机和平板都方便。生命周期大致是：
    onAttach -> onCreate -> onCreateView -> onViewCreated -> onActivityCreated -> onStart -> onResume -> onPause -> onStop -> onDestroyView -> onDestroy -> onDetach。

  5. 最满意的模块，以及里面用到的设计模式。 嗯……当时没答好。

  6. HTTPS。 就是 HTTP + TLS/SSL。

单独说一下 Looper 和 Handler

  • 每个线程有一个 Looper，Looper 内部有一个 MessageQueue。
  • Handler 可以在任意线程发送消息，消息都会进入它关联的 Looper 的 MessageQueue。创建 Handler 时会关联一个 Looper，不指定就是当前线程的 Looper。
  • Looper 不断轮询自己的 MessageQueue，把消息交给 Handler 的 handleMessage() 处理。

调用 Looper.loop() 之后，Looper 才开始工作。

线程相关的内容见《Java 线程状态》，线程池见《Java 线程池》。

某怡科技

Android 负责人技术还行，感觉是对着《Android 开发艺术探索》来面的。不过这本书确实经典。

  1. 线程池有哪几种实现

    • FixedThreadPool：线程数固定的线程池。
    • CachedThreadPool：线程数上限很大，有任务就创建线程；空闲 60 秒的线程会被终止并从缓存移除，全部闲置时线程池不占内存。
    • ScheduledThreadPool：核心线程数固定，非核心线程数不固定，闲置就回收，适合定时和周期性任务。
    • SingleThreadExecutor：只有一个线程，任务串行执行。

  2. onMeasure 参数的意义
    MeasureSpec 是 32 位的值，高 2 位是 SpecMode，低 30 位是 SpecSize。SpecMode 有三种：

    • UNSPECIFIED：父容器不对 View 做任何限制。
    • EXACTLY：父容器已经确定 View 的具体大小，最终大小就是 specSize。
    • AT_MOST：父容器给了一个可用的 specSize，View 不能超过它。
      MeasureSpec 由 LayoutParams 和父容器共同决定：
    • match_parent：大小就是窗口大小。
    • wrap_content：大小不定，但不能超过窗口大小。
    • 固定 100dp：就是 LayoutParams 指定的大小。
      子元素的 MeasureSpec 和父容器的 MeasureSpec、子元素自己的 LayoutParams，以及 margin、padding 都有关系。
      写自定义 View 时，如果自身是具体尺寸，SpecMode 就是 EXACTLY；如果是 match_parent，不论 EXACTLY 还是 AT_MOST，拿到的都是 parentSize；如果要支持 wrap_content，就必须重写 onMeasure，因为此时 SpecMode 是 AT_MOST，不处理的话会填满父控件。做法是在 onMeasure 里判断 AT_MOST，用默认宽高代替。

  3. 自定义绘图、旋转。 用 matrix.setRotate()，当时被追问了 Matrix 和 Bitmap 的关系。

  4. 图片三级缓存
    网络缓存：不优先加载，速度慢、费流量；本地缓存：次优先；内存缓存：优先加载，速度最快。

  5. Activity 的启动过程。 见《Activity 启动和 Service 启动》。

  6. IntentService
    Service 运行在主线程，所以不能直接做耗时操作。能执行耗时任务的 Service，内部靠 HandlerThread + Handler 实现，而 HandlerThread 就是带 Looper 的 Thread。也正因为如此，IntentService 处理完所有逻辑后会自动关闭服务（这么厉害的东西，之前居然没用过）。

  7. 图片缓存回收算法
    LRU，最近最少使用：

    1. 新数据插入链表头部。
    2. 缓存命中时，把该数据移到链表头部。
    3. 链表满时，丢弃链表尾部数据。
      LruCache 由 LinkedHashMap 实现，内部做了同步（会被不同线程调用）。图片缓存里存的是 Drawable。

  8. 并发场景下怎么争夺资源。 就是 synchronized。

扩展问题

  1. 数据结构有哪些
    逻辑结构分为集合、线性、树形、图形；物理结构分为顺序存储（数组）和链式存储（链表）。
    常见的有：数组 String[] 以及 ArrayList 这类列表、LinkedList、栈（Activity 任务栈就是先进后出）、队列（FIFO）、树、图。

  2. Java 的 CopyOnWrite 思路。 各种集合类的实现见《Java 集合理解》。

  3. Android 热修复原理。 见《Android 热修复原理》。

  4. Android 保活

    • 不同 App 利用广播相互唤醒。
    • 开前台服务但不显示 Notification，这种方式还是会被杀。
    • 如果够厉害，进系统白名单。
    • 一个像素的 Activity。
    • JobScheduler（当时还没验证过怎么用）。
      进程回收靠的是 Low Memory Killer，oom_adj 越低越不容易被杀。App 退到后台后，所有进程优先级都会降低，UI 进程降得最明显，因为它占的内存最多。所以内存紧张时，系统会优先杀这些占用高的进程。想尽量保命，就得在后台主动释放不用的资源，尤其是图片、音视频。
      目前来看，App 进入后台后只要资源紧张，基本一定会被 kill。

  5. 生产者消费者模式。

  6. Android 优化

    • 内存泄漏。
    • UI 绘制慢导致卡顿。
    • StrictMode 严苛模式。
    • 启动优化：不必在 Application 里初始化的代码，放到 UI 初始化完成之后。

  7. Socket 的基本流程
    服务端先 socket() 创建套接字，再 bind() 绑定端口、listen() 监听；客户端 socket() 之后调用 connect() 发起连接；服务端 accept() 拿到连接后，双方就可以通过 read() / write() 收发数据，最后各自 close()。
