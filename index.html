TraceDock：让 AI 自己点手机抓日志，一次 Android 排查的自动化实践

Posted on 2026-10-22

做 Android 这些年，最费时间的从来不是写页面，是排查问题。

用户说「登录一直转圈」，你把手机连上电脑，adb logcat 刷屏，几万行日志滚过去；页面在哪个 Activity 不知道，用户点的是哪个按钮不知道，那个请求是第几次重试触发的也不知道。最后能定位问题的那几十行，往往夹在几千行无关日志中间。这套流程我重复了很多年，每次都在做同一件事：手工重现、手工翻日志、手工把请求和响应配对。

TraceDock 就是为这件事做的。它是我在组内 Q4 主推的一个本地工具，现在的状态是开发完成、正在测试验收、准备 11 月推给组内同事用。

一句话说清楚它干什么：

选好应用与设备，描述一句问题，或者干脆给一张「要操作的页面」的参考图，点开始。剩下的它自己来 —— 自己操作手机找到目标页面、触发请求、把日志收上来，最后给你一份能对回原始日志 id 的排查结论。

开始之后不用碰手机，可以继续干别的活。这不是演示视频里的效果，下面会给出真机跑出来的完整数据。

模块化浅析

Posted on 2017-05-11

子曰：简单性和模块化是软件工程的基石；分布式和容错性是互联网的生命。

这篇的标题挂了很久，正文一直空着，补一段自己的理解。

模块化说白了就是把一个 App 拆成几块：基础库放网络、图片、工具类这些谁都要用的东西；业务模块按功能切，比如登录、订单、消息；最外面留一个 app 壳，负责组装和打包。每块单独一个 module，依赖关系单向，业务模块之间尽量不互相引用。

好处很直接。改一个业务模块，只编译它和 app 壳，不用每次全量编译，等的时间少很多；几个人可以同时改不同的模块，冲突也少；哪天要把这块逻辑搬到别的 App，整个 module 拿过去就行。

RecyclerView

Posted on 2017-03-08

优点

RecyclerView 本身不关心视图相关的问题。ListView 的耦合太紧，Google 的改进就是让 RecyclerView 不参与任何视图相关的事：它不关心怎么把子 View 放到合适的位置，不关心怎么分割子 View，更不关心每个子 View 各自长什么样。

再进一步说，RecyclerView 只负责回收和重用，这也是它名字的由来。

所有跟布局、绘制以及数据展示相关的问题，都委派给了一些「插件化」的类来处理，这让 RecyclerView 的 API 变得非常灵活。需要新的布局？换一个 LayoutManager 就行。想要不同的动画？接一个 ItemAnimator 就行，诸如此类。

app启动优化

Posted on 2017-03-02

先量一下启动时间

用这条命令查出启动时间。Application 的初始化可以放到线程里做。

为什么不能卡在生命周期里

启动相关的这些阶段全部都在主线程执行，任何不经意的操作都可能拖慢启动速度。所以不应该在 Application 以及 Activity 的生命周期回调里做费时操作。

具体指标大概是：onCreate、onResume、onStart 等回调里花的总时间最好不要超过 400ms，否则用户从桌面点开应用图标后，会感觉到明显的卡顿。

但有些任务又不得不在 UI 显示之前执行，所以要把任务划分优先级：

  1. 优先级 1：应用启动时就开始加载。
  2. 优先级 2：首页渲染完成后再开始加载。
  3. 优先级 3：首页渲染完成后再延迟加载，用 postDelayed 的方式。

android中的各种位置

Posted on 2017-02-28

View 提供的获取坐标方法

  • getTop()：View 自身的顶边到其父布局顶边的距离。
  • getLeft()：View 自身的左边到其父布局左边的距离。
  • getRight()：View 自身的右边到其父布局左边的距离。
  • getBottom()：View 自身的底边到其父布局顶边的距离。

MotionEvent 提供的方法

  • getX()：点击事件距离控件左边的距离，即视图坐标。
  • getY()：点击事件距离控件顶边的距离，即视图坐标。
  • getRawX()：点击事件距离整个屏幕左边的距离，即绝对坐标。
  • getRawY()：点击事件距离整个屏幕顶边的距离，即绝对坐标。

把这两组方法放在一起看，应该就能对 MotionEvent 和 Android 坐标系有个比较清楚的认识了。

activity启动和service启动

Posted on 2017-02-24

Activity 和 Service 是 Android 里最重要的两个核心组件，平时研究得也比较多。

startService 和 bindService 的区别

  • startService() 启动：Service 接收 Intent，经历 onCreate() 和 onStartCommand()；调用方发出停止意图后，走 onDestroy()。
  • bindService() 启动：和 Activity 绑定时，经历 onCreate() 和 onBind()；Activity 被销毁时，先走 onUnbind()，再走 onDestroy()。
  • 用 startService 启动的服务和调用者没有关联，即使调用者退出了，服务仍然在运行。
  • 用 bindService 启动的服务和调用者绑在一起，调用者一旦退出，服务也就终止了。

android热修复原理

Posted on 2017-02-22

当时常用的热修复技术，大概分三类：

  • AndFix：Native hook 方案。
  • Nuwa、HotFix、RocooFix：QQ 空间提出的 ClassLoader 替换类方案。
  • Tinker：Instant Run 冷插拔原理的 Dex 替换。

Native hook

在 native 层做指针替换。AndFix 基于修复包和原生包的差异生成注解，通过这份注解找到要替换的方法，条件满足就 hook 掉并替换。

Dex 分包

Nuwa、HotFix、RocooFix 这些方案都是基于 dex 分包。

什么是 dex 分包？先看 DexOpt。Android 系统安装一个应用时，有一步是对 Dex 做优化，专门干这事的工具叫 DexOpt。它在第一次加载 Dex 文件时执行，会生成一个 ODEX 文件，也就是 Optimised Dex。ODEX 的执行效率比直接执行 Dex 高很多。

rxjava转换操作符

Posted on 2017-01-22

转换操作符

buffer

buffer 会周期性地把源 Observable 产生的结果收集到列表里，再把这个列表提交给订阅者。订阅者处理完之后清空 buffer 列表，同时接收下一次收集的结果并提交，周而复始。

flatMap

flatMap 把 Observable 产生的结果转换成多个 Observable，再把这多个 Observable「扁平化」成一个，并依次把产生的结果提交给订阅者。

concatMap

concatMap 和 flatMap 类似，也是把结果转换成多个 Observable，再扁平化成一个。区别在于 concat 是有顺序的，会按源数据的顺序依次合并。
