TraceDock：让 AI 自己点手机抓日志，一次 Android 排查的自动化实践

Posted on 2026-10-22

做 Android 这些年，最费时间的从来不是写页面，是排查问题。

用户说「登录一直转圈」，你把手机连上电脑，adb logcat 刷屏，几万行日志滚过去；页面在哪个 Activity 不知道，用户点的是哪个按钮不知道，那个请求是第几次重试触发的也不知道。最后能定位问题的那几十行，往往夹在几千行无关日志中间。这套流程我重复了很多年，每次都在做同一件事：手工重现、手工翻日志、手工把请求和响应配对。

TraceDock 就是为这件事做的。它是我在组内 Q4 主推的一个本地工具，现在的状态是开发完成、正在测试验收、准备 11 月推给组内同事用。

一句话说清楚它干什么：

选好应用与设备，描述一句问题，或者干脆给一张「要操作的页面」的参考图，点开始。剩下的它自己来 —— 自己操作手机找到目标页面、触发请求、把日志收上来，最后给你一份能对回原始日志 id 的排查结论。

开始之后不用碰手机，可以继续干别的活。这不是演示视频里的效果，下面会给出真机跑出来的完整数据。

一、它到底解决谁的什么问题

先把背景说清楚，不然容易看成一个「AI 玩具」。

我们组做的是 Android App，日常排查集中在两类：

  • 崩溃 / ANR：堆栈能拿到，但要还原「崩溃前用户干了什么」很痛苦
  • 接口问题：请求发了没回、回了但字段不对、登录态掉了、签名校验失败

这两类问题的共同点是：现象在界面上，证据在日志里，而中间那段链路只能靠人手工补。尤其接口问题，一次页面跳转会打出十几条请求，你得自己判断哪条是目标、它的响应体在哪、中间有没有重试。

所以这个项目的目标不是「让模型看日志说话」，而是把整条链路自动化：

验收标准我也定得很朴素，写在交接文档里：判断标准是「同事能不能自己用起来」。

这条标准直接推导出一条设计原则，我叫它「无感」：用户只做三件事 —— 选应用与设备、说一句问题（或者给张参考图）、点开始。任何要求用户先理解日志格式、采集参数、点击路线的环节，都按缺陷处理，不是「文档里写一下就行」。

另一条是「有据」：结论必须能对回真实日志 id。没有证据就老老实实写缺口，不许用「可能」「应该」糊过去。

二、整体链路长什么样

项目是本地跑的，服务默认只监听 127.0.0.1:8766，不对外。这个选择是刻意的：它要操作手机、要读源码、要把日志发给你配的模型，这些都不该离开本机。

完整链路是这样：

前段是「把日志收干净」，中段是「从几万条里挑出该看的那几百条」，后段是「让模型在这几百条上做判断，并且必须给出引用」。

中间那条预筛链路是整个项目的技术核心，第五节细讲。

三、技术栈：克制到什么程度

先把实证摆出来，避免空谈。

后端 pyproject.toml 里运行时依赖只有 5 个：

没有 ORM，没有任务队列，没有缓存中间件。数据库用标准库 sqlite3，开 WAL 模式；日志原文按会话落成 raw.log，库里只存索引和结构化字段。

这不是「不会用」，是这个场景不需要：

  • 单人本地工具，没有并发压力，SQLite 完全够
  • 装一个 Redis 或 Celery，只会让同事的启动步骤变长
  • 依赖越少，出问题越好查，换台机器越好装

前端是 React 19 + Vite 6 + TypeScript 5.7，UI 组件自己写，只有 lucide-react 一个图标库。测试用 vitest 3 + Testing Library，大约 40 个组件，每个组件旁边都有一份 .test.tsx。

后端分了 29 个模块，职责切得比较细，主要几块：

模块 职责
capture / device_control logcat 采集、ADB 动作
store SQLite 会话与日志索引
modules.prescreen 日志预筛（锚点 + 扫描）
selection / request_context 400 条预算内的日志挑选与请求上下文拼装
investigation / case_analysis 诊断主流程
analysis / live_analysis 分析任务调度与流式输出
autonomy / autonomy_api 自主任务：截图 → 判断 → 动作 → 复检

当前的测试状态：

项 结果

前端类型检查 tsc --noEmit 通过
前端生产构建 tsc -b && vite build 通过

写测试这件事，在这个项目里不是为了覆盖率好看。因为核心链路是「模型输出 → 本地校验 → 执行动作」，任何一个环节放宽校验都会变成一个线上事故，所以每条约束都配了用例。

四、最难的不是调模型，是把边界画死

AI 自动操作手机，听起来最玄的是「模型看得懂页面」。实际做过就知道，模型看得懂反而是最容易的部分，难的是你敢让它动手到什么程度。

4.1 动作白名单 + 新鲜观察

模型能发出的动作只有这几个：tap / swipe / back / wait / input / login / finish / blocked。

每个动作执行前，必须先拿到一次新鲜的页面观察（截图 + 界面结构）。如果这次观察已经过期，直接抛 StaleObservationError，动作不执行，重新观察。

这条规则是踩坑踩出来的。测试中遇到过：模型看完截图决定输入账号，但那一步等了太久，界面已经自己跳走了，结果文字被输到了另一个页面的输入框里。现在输入动作前的观察失效被视为「可重新观察的异常」，而不是一个需要宽容的错误。

4.2 危险动作在本地拦，不靠模型自觉

支付、下单、删除这类按钮，一律由本地执行器拦截，不依赖提示词里那句「请不要点击危险按钮」。

同样，凭据只从环境变量 LOGTRACING_TEST_CREDENTIALS 读，login 动作在本机一次性注入，不进模型上下文，相关截图做遮挡。模型知道「需要登录」，但不知道该用什么账号。

4.3 每个动作前记游标，只认边界之后的证据

这是「有据」落到代码上的方式。

每个动作执行前保存一次日志游标。动作完成后，只接受这个游标之后新发起的请求与响应作为证据。这样就不会出现「上一轮页面留下的响应，被当成本轮动作的结果」这种假阳性。

对应地，证据状态只有三种，不允许模糊：not_observed / request_observed / response_observed。

4.4 状态机和上限

自主任务的状态是 queued → running → blocked / completed / error / cancelled / interrupted，阶段是 checking / navigating / waiting / analyzing / finished。

三道硬上限：最多 30 步、360 秒、单次分析 120 秒。超了就停，不是无限循环。

blocked 这个状态我要求得很严：必须写清楚缺什么、谁来做、怎么继续。写不出来就不许用 blocked 糊过去。这条规则来自一次真实故障 —— 导航时设备操作报错，异常一路冒到兜底逻辑，任务被标成 error，看起来像代码 bug，实际只是需要人去点一下屏幕上的授权弹窗。现在首次拦截会写进时间线并要求改用只读动作，第二次才升级为 blocked。

五、锚点机制：一个真实性能缺陷的修复

这一节是我最想写的，因为它完整地体现了「怎么发现、怎么定位、怎么修、怎么防回归」。

问题

自主任务流程是：AI 自己操作手机 → 找到目标端点 → 停采 → 把这个端点交给分析链路。

分析链路的日志预算默认是 400 条。预筛阶段先按关键词扫描，扫描上限 SCAN_CAP = 20000。

真机上跑出来的会话是 3 万多条日志。目标请求确实抓到了，日志 id 很靠后，但它在 2 万条扫描窗口之外 —— 于是被直接漏掉。模型拿到 400 条日志，里面没有目标请求，结论自然是错的。

这个 bug 最阴的地方是：它不报错。任务显示成功，分析显示完成，只是结论不对。如果没有真机验收，纯靠单元测试根本发现不了。

修法

自主任务结束时，把已经确认的 _target_endpoint 传给 analysis.start(..., anchors=[...])。

预筛阶段先用 search LIKE %anchor% 从全库直取命中日志（ANCHOR_CAP = 200），并排在整个扫描结果的最前面。然后在拼装请求上下文时，RequestContextBuilder 给命中锚点的请求单元最高优先级，并且在裁剪到 400 条预算时跳过它们、不参与淘汰。

效果是：不管会话有几万条日志、目标日志 id 排得多靠后，只要端点识别是对的，它一定在最终送给模型的那 400 条里。

这个设计还有个直接的好处 —— 锚点不是「猜」出来的关键词，而是上一阶段真实验证过的端点，所以它的准确率比任何启发式规则都高。

当然它也有边界：如果上游端点识别错了，锚点保护不到。这一条我写进了已知问题，没藏。

六、另一个坑：SQLite 整库变只读

这个故障值得单独说，因为它跟业务代码一行关系都没有。

现象是：某台机器上，写入全部失败。日志里 SQLite 报只读，但文件权限看起来正常。

查下去发现，data/ 下的库文件和两个 WAL 边车文件被外部程序加上了 SHR 属性（只读 + 隐藏 + 系统），还带云文件标记。SQLite 打开连接时看到只读属性，就把整库当成只读库处理，于是所有写操作失败。

修法是两层：

  1. 每次建立连接前，清掉这几个文件的只读/隐藏/系统属性，并把过程记进 stderr，出问题能对上时间点
  2. 写失败统一返回 503，附一句人能看懂的话，而不是把 SQLite 的原始错误直接抛到界面上

第 2 点其实是这个项目一直坚持的做法：错误信息是给同事看的，不是给日志看的。

七、真机验收：把数字摆出来

没有真机数据的 AI 项目，可信度等于零。所以这部分我写得很细。

我把这些 ID 都写进了验收文档。原因很简单：出问题的时候，能顺着 id 复现到同一次运行，比任何描述都管用。

八、源码为什么是「必需输入」，不是「可选增强」

这个项目有一条 P0 规范，我写在 AGENTS.md 里，语气比较硬：

源码是必要输入，不是可选增强项。配置存在、快照存在或展示「结合源码」标签均不算完成。必须实际检索并向已授权模型提供目标模块相关实现，结论引用服务端校验过的片段 id、文件和行号，并与真实日志 id 对照。只有域名常量等背景代码不能代替接口调用与响应消费逻辑的对照。

为什么这么定？

因为只看日志能做的是「现象描述」，不是「原因定位」。日志告诉你「这个接口返回了 401」，但「这次 401 是被哪段降级逻辑吞掉的」「这个字段前端到底怎么解析的」，只有源码能回答。

所以实现上做了一整套约束：

  • 源码是固定快照，不跟着仓库实时变，保证同一份日志 + 同一份代码可以复现结论
  • 检索是有界的，不把整个工程塞进上下文
  • 发送的片段做脱敏，单文件超 512 KiB 截断，源码缓存默认 2 GiB
  • 模型给出的引用由服务端校验，对不上的引用不算数
  • 设备操作、日志、源码发送是三份分别授权，不是一次同意全开

这里也有一个现实约束：源码不是想读就能读。这个项目对接的是公司 GitLab 上的仓库，我在做的时候只能拿到目标模块的相关文件做快照，所以验收结果是「在 AEG 登录这一条链路上跑通」，而不是「所有模块都通过」。

九、踩过的坑，以及坑告诉了我什么

挑几个有代表性的。每条都是「真故障 → 真修复 → 真回归」。

Android 16 的 dumpsys window windows 不再返回 focus 信息。 界面结构解析直接拿到空焦点。修法是补 displays 作为兼容来源，而不是硬编码版本号判断。

模型把动作参数嵌在 tap 子对象里，被严格校验拒绝。 当时的诱惑是「放宽校验让它过去」。我没有。做法是给模型加扁平化的参数示例，并允许一次自我纠正。白名单和参数结构一个都没松。理由是：今天为兼容模型输出放宽的每一条校验，明天都会变成一个无法解释的现场。

截图一变，预先规划的动作就失效。 这是前面说的新鲜观察机制的直接来源。现在输入类动作前如果观察失效，视为可重新观察的异常，重新截图再决策。

请求日志里没有加密 query，响应里却附带了 query。 两个日志条目对不上，无法配对。修法是很窄的回退规则：只允许「同线程 + 唯一候选 + 已 END + 原请求无 query」的同端点回退匹配。窄规则意味着宁可配不上，也不乱配。

导航循环只捕获 StaleObservationError，DeviceControlError 冒到了兜底。 结果一次正常的系统授权弹窗把任务标成了 error。修法见 4.4。

这些坑有一个共同点：它们都不在「模型能力」这一层，而在「系统和模型之间的契约」这一层。这也是我做完这个项目最大的感受 —— AI 应用真正的工作量，不在调用模型，而在把模型的自由度收敛到一个可以验收的范围里。

十、边界：现在还不能吹的地方

写技术文章最容易犯的错是把「跑通了」说成「做完了」。这个项目的边界我列清楚：

  • 自主排查只在 AEG Ecohome 登录场景完成了真机验收，不能声称所有模块、所有起始状态、所有应用都通过
  • 如果设备已经是登录态，抓不到登录接口本身
  • 服务重启会丢进程级的凭据，需要重新注入
  • 端点识别错误时，锚点机制保护不到
  • data/autonomy/<任务ID>/ 目前不会自动清理
  • Windows 端到端稳定，macOS 有启动脚本但真机端到端还没验收
  • 还有偶发测试失败未定位根因，没有当成「环境问题」糊过去

11 月推广给组内使用，我给自己定了 5 条门槛，其中核心的还是那一条：同事能不能不看文档、自己跑起来一次完整排查。做不到就还不算完成。

十一、这个项目里，我做了什么

最后说点实在的。这个项目是在 AI 协作下完成的 —— 需求定义、架构拆分、模块边界、验收标准、真机验收和故障定位由我负责，具体实现和测试有 AI 一起写，565 个后端用例和 162 个前端用例也是在这个流程里堆出来的。

我更愿意把它描述成「AI 赋能的全栈」：我一个做了多年 Android 的人，用 Python + FastAPI + React + TypeScript 把一个「操作手机、采日志、结合源码、出证据」的完整工具做了出来，并且能给出真机数字和已知缺陷清单。

如果只看代码量，这个项目不算大。但它把三件事串起来了：

  1. 产品判断：把「无感」和「有据」变成可执行的验收标准，而不是口号
  2. 工程判断：依赖只有 5 个，动作白名单不放宽，引用必须服务端校验
  3. 交付判断：用真机数据说话，把边界写在文档第一屏

这三点，比「用了什么框架」更能说明问题。

项目现在在公司内网 GitLab，跑在本机 127.0.0.1:8766。等 11 月推完组内，我再回来补一篇「推广之后遇到的问题」。
